# /breakdown - 把一条任务拆细

只处理**一条**任务：它的第一步是什么。产出一条 `updates` 建议，改 `subtasks`。

跟 `/review` 的区别：那个是**撒网**——扫一遍全部任务，找出值得说的；这个是**点射**
——他已经指着这一条说「太粗了，帮我拆」。所以这一轮**不产 `insights`**、不看别的
任务、也不提别的字段。

**你不直接改任务。** `updates` 会变成一条挂在那张卡片上的建议，等他点「接受」或
「忽略」。字段白名单、`reason` 必填这些规矩在 `AGENTS.md`「提修改建议」那节，
这里不重复。

## 这次只有一条任务

叫你的那句话里带着范围：「这次只处理任务「…」（id 为 …）这一条……」——**那个 id
就是你要处理的全部对象**，别去猜、别顺手多拆一条。

调接口那条路上（设置里选了「调接口」），你收到的 `data/tasks/` **已经筛过了**，
里面最多两条：

- **这一条**任务本身；
- 加上 `parentId` 指着它的那些**直接子任务**。

子任务一起给你是有原因的：一条项目型的任务，它的「下一步」可能已经以子任务的形式
躺在下面了。你要回答的是「**还差哪一步**」，所以得先看见已经有哪些。

`data/lists/` 也贴给你了，但**这一轮用不上**——见下面「只改 `subtasks`」。
`data/insights/` 没贴，因为这一轮你不写观察，用不着为了「别重复说过的话」去读一份
自己不会写的东西。

## 他自己在会话里说的时候，那一条得自己找

上面那种是**服务**叫你：那句话里带着 id，照它办就行。而他自己开一个会话敲
`/breakdown 装修` 的时候——**没有那句话**，他给的就是「装修」这三个字。

- **去 `data/tasks/` 里按 `title` 找。** 找得到唯一一条就照它办，往下跟服务叫你
  时完全一样。
- **对上不止一条、一条都对不上、或者他压根没说是哪条**：回 `[]`，并在回复里
  把情况说清楚（「叫『装修』的有三条，你说的哪一条？」）。**别挑一条看起来最像
  的**——拆错了对象，他点一下「接受」，那几步就长在另一条任务上了。
- **别把「找不到」当成「那就全拆一遍」。** 这一轮的对象永远是一条，不是一批。
- 自己找的那条**一样要守**下面所有规矩（已经够具体就回 `[]`、已有待决建议就跳过、
  提的必须是完整的一份）——那些跟范围是怎么来的无关。

## 只改 `subtasks`，别的字段一个都不提

这一轮唯一该产出的东西是 `subtasks`。`title`、`due`、`tags`、`priority`、`listId`、
`waitingFor` 这些**都别碰**：他点的是「拆细」，不是「顺便帮我改改这条」。想说的
别的（这条该归到哪个清单、是不是该往后挪）留到下次 `/review`——那时候他会主动要，
而这一轮里混进去的每一条，都让他多分辨一次「我没要这个啊」。

`status` 更别碰——**它不在 `PROPOSABLE` 里，出现一次整个 outbox 文件校验不过**，
这一轮的建议全跟着丢（正本在 `server/src/task.ts`）。

## 提的 `subtasks` 必须是**完整的一份**，不是新加的那几条

接受一条改 `subtasks` 的建议是**整字段替换**——跟 `notes` 一样，服务端
（`mutate.ts` 的 `applyTaskPatch`）里写的是 `patch.subtasks ?? prev.subtasks`，
不合并、不留历史。垃圾箱只接被删除的任务，救不了一次误接受。

所以：

- 这一条**已经有子任务**的：你提的数组要**把它们原样带上**——`text` 一个字不改，
  `done` 照抄（**已经划掉的那些也要带上**），后面再接你新加的。
- 漏掉已有的那几条 = 他点一下「接受」，那几步**当场消失**，而它们可能已经做完了。
  这是这一轮最容易犯、也最贵的错。

## 拆成什么样才算对

- **一步一个动作**，每一条都能单独做完、单独打勾。「准备材料」不是一个动作，
  「把三份合同找出来拍照」是。
- **三到六条**。给十条他不会照着做；只给一条等于没拆。
- **第一条是「现在就能动手的那一下」**——他点「拆细」多半就是因为不知道从哪儿下手。
- **不写序号**（「1. 」「第一步：」）。子任务本来就有顺序，序号是多余的，
  而且他拖动排序之后那几个字就变成假的了。
- **别把整件事重述一遍当子任务**（「完成装修」不是装修的第一步）。
- 备注（`notes`）里的东西——项目的方向、当时的想法、他对着编码 AI 说过的原话
  ——是你**判断该怎么拆的依据**，不是待改的东西。这一轮不碰 `notes`。

## 已经够具体了就说没有

这条任务本来就够小（「把快递单号发给张老师」），拆出来的子任务只会是同一句话换个
说法。**这时候回空数组 `[]`，如实说「这条已经够具体了」**——那是有用的答案，不是
失败。凑数造几条出来比不提更糟：他每看一条没用的建议，下一条真有用的就少一分信任。

`habit: true` 的**直接回 `[]`**：习惯没有「第一步」（「晨跑」拆不出第一步来），
`/review` 那份文档里有一整段讲这个。

## 这条任务上已经有待决建议的就跳过

`data/proposals/` 里，如果这条任务上已经挂着一条你提过、他还没处理的建议，**回 `[]`**。
同一张卡上摆两条建议，他得先分辨哪条是哪条。

（他**忽略过**的建议是另一回事：那是在否掉那个意见，不是「这条任务以后都别管」。
情况真的动了、你算出来的是不一样的内容，照样提。）

## 组装 updates，写 outbox

```json
[
  {
    "updates": [
      {
        "id": "这一条任务的 id",
        "patch": {
          "subtasks": [
            { "text": "…", "done": false }
          ]
        },
        "reason": "一句话说清你为什么这么拆"
      }
    ]
  }
]
```

- `updates` 那一项的 `id` **就是叫你的那句话里那个 id**，别去猜、别自己造。
- 一条任务一条 `updates` 项。这一轮**不写 `insights`**（不产观察）、**不写
  `tasks`**（收件箱那套跟这里无关）——`AGENTS.md` 说三种条目各占数组里的一项，
  这一轮只会用到 `updates` 这一种。
- 原子写：先写 `outbox-<unique>.json.tmp`，写完整再改名成 `outbox-<unique>.json`。
  临时名不能是 `outbox-` 开头又 `.json` 结尾，理由见 `AGENTS.md`。

## 回复里说清楚

拆成了哪几步、为什么这么拆。他在不打开网页的情况下要能判断你这一轮跑得对不对。

## 这个不是自动跑的

只在他在卡片 ⋯ 菜单里点「让 AI 拆细」时跑。没有自动触发，也没有定时任务——
什么时候拆、拆哪一条，都是他指着说的。
