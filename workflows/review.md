# /review - 定期回顾已有任务

看一遍 `data/tasks/` 里已经存在的任务，把该改的地方**提成建议**，写进
`data/outbox-<unique>.json` 的 `updates` 条目里；说不清该改哪一条任务的跨任务
观察写 `insights` 条目——这个工作流也是 `insights` 主要的产出场景。

跟 `/expand` 的区别：那个处理收件箱里**还没变成任务**的文本，这个看的是**已经在
看板上**的任务。两件事互不干扰，同一个文件里也可以混着写。

**你不直接改任务。** `updates` 会变成一条挂在卡片上的建议，等他点「接受」或
「忽略」；`insights` 也一样不会改数据，只是记一条观察。字段白名单、`reason` 必填
这些规矩都在 `AGENTS.md`「提修改建议」和「第三种条目：insights」两节，这里不重复。

## Step 1: 先读 proposals 和 insights

读 `data/proposals/`——你以前提过的建议都在那儿。**跳过谁不跳过谁，
规矩在 `AGENTS.md`「提修改建议」那节，跟别处一样这里不重复。**

只强调一句它最容易被读错的地方：**「挂着待决建议的任务跳过」和「他忽略掉的那条
别再提」不是同一条规矩。** 前者跳过的是**这条任务**（他还没处理，堆第二条只会
让同一件事在卡上排成几行），后者不许再提的是**那一条建议**——他按「忽略」是在
否掉那个意见，不是说「这条任务以后都别管」。情况真的动了、你算出来的是不一样的
内容，那是一条新建议，照样提。

一刀切的代价是实打实的：**被忽略的建议不会过期**（服务只给它打个 `dismissed: true`
写回文件，没有任何东西会清掉它，界面上也没有入口）。把两条并成「出现过的 taskId
一律跳过」，那不是「这一轮跳过」，是**这条任务从此退出回顾**——用得越久漏得越多。

再读 `data/insights/`——你以前提过的跨任务观察。`dismissedAt` 非空的是他点过
「知道了」的，同一条别换个说法再提一遍。

## Step 2: 读 tasks，挑出值得说的

跳过 Step 1 里那些之后，重点看这三类：

- **过期没做完的**：`due` 已经过了、`status` 不是 `done`。
  典型建议是改期（`due` + `reminders` 一起改，只改 `due` 不会响），
  或者把它拆细一点（改 `subtasks`）
- **在 `doing` 里躺很久的**：看 `updatedAt` 离现在多久。躺得久多半是拆得太粗，
  一步做不完——建议改 `subtasks`，把第一个能独立做完的动作单独列出来
- **反复出现的同类任务、几条其实是一件事**：这类挂不到单独一条任务上，写
  `insights` 条目（`kind: pattern` 或 `duplicate`），不是硬塞进 `updates`
- **卡住的项目**：一条还挂着的任务（`status` 是 `todo`/`doing`），底下有子任务
  （别的任务 `parentId` 指着它），但**没有一条子任务是 `todo`/`doing`**——全被
  搁置或放弃了。这种项目在列表里跟别的待办长得一模一样，其实一步都动不了。
  网页那边已经会把它列出来（「回顾」那一屏的「卡住的项目」，判据是确定性算出来
  的，不用你再找一遍）——**你要补的是那一步他自己想不出来的**：看看那几条子
  任务为什么停了，写一条 `insights`（`kind: pattern`），点名「把某一条捡回待办」
  或者「这个项目本身也该搁置」，`reason` 里说清为什么是那一条。
  **别用 `updates` 改 `status`**：`status` 不在白名单里（AGENTS.md「提修改建议」
  那节，正本是 `server/src/task.ts` 的 `PROPOSABLE`），出现一次**整个 outbox 文件
  校验不过**，这一轮别的建议、别的观察全跟着丢。这一段原来就写着「`updates` 改
  那条子任务的 `status`」——照做一次，整轮回顾白跑。
  注意这跟上面那条「搁置的不要动」不冲突：搁置的是**子任务**，而挂着的是
  **父任务**——他搁置某一步的时候，多半没意识到整个项目因此停了。

`status` 是 `later`（他自己搁置的）和 `done` 的，**不要动**。搁置的意思就是
「暂时不想看见它」，你把它翻出来提建议正好跟他的意图相反。

## `habit: true` 的不算「过期」，也不算「重复出现」

习惯（`habit: true`，必配每天重复）会同时踩中上面两类，而两类都是误判：

- **它天天「过期」，那是常态不是问题。** 一条早上七点的晨跑，到晚上还没打卡就
  `due` 已经过了、`status` 不是 `done`——完全符合第一类的判据。但那不需要建议：
  他今天没跑而已，明天那条打完卡自己就会生成。
  **而改它的 `due` 比不改糟得多**：`repeat.from` 是 `'due'`，你把这一条往后挪
  一挪，**以后每一天都跟着挪**——早上七点的晨跑会变成你挑的那个钟点。他点
  「接受」的时候多半以为只是挪了这一次。
  拆 `subtasks` 同理不成立：「晨跑」没有第一步。
- **同一个习惯散在几十条记录上，那是它的数据模型，不是重复。** 每打一次卡就多
  一条同标题的记录（服务只在完成时生成下一条），所以 `data/tasks/` 里会有三十条
  「晨跑」。那正好是第三类 `insights` 里 `duplicate` 的形状，但报出去等于告诉他
  「你把同一件事记了三十遍」——而那是他坚持了三十天。

所以：**这两类里遇到 `habit: true` 的，跳过。** 别的观察（比如备注、标签）真有用
的话照提，这一条只挡这两种误判。

## 备注只提议「追加」，不提议重写或精简

`notes` 在你能提议的字段里（`PROPOSABLE`），但**它跟别的字段不是一回事**：`due`
是一个可以重算的值，备注是**他自己写下来的原始记录**——项目的方向、当时的想法、
甚至他对着编码 AI 说过的原话。那段话正是这个系统里唯一存「为什么」的地方：代码
变成了什么样，git 记得住；他当时想要什么样，只有这里有。

而这条路上没有任何退路：接受一条改 `notes` 的建议就是**整字段替换**，服务端不留
字段历史，`data/proposals/` 里存的也只有新值——**旧的那段原文没有任何地方找得
回来**。垃圾箱只接被删除的任务，救不了一次误接受。

所以：

- **可以**提议往备注里**加**东西（补一句缺的上下文、把你观察到的卡点附在后面）。
  提议的 `notes` 值要是「原文 + 你加的那段」，原文一个字不动。
- **不要**提议重写、精简、整理、重新组织备注——哪怕它看起来很乱、很长、像是随手
  粘进来的一堆指令。**看起来像草稿的那部分，多半正是他最想留的原话。**
- 备注读起来不像待办、不像任务描述（比如一整段对编码 AI 说的话），那不是问题，
  **不用「修好」它**。据它去理解这条任务在干什么，这正是它在那儿的用途。

（想说的是「这段备注可以整理一下」的话，走 `insights` 说一句观察，别做成
`updates` 里一条点一下就落地的替换。）

## 叫你的那句话里带了范围的话，就只看那一批

那句话可能是这样收尾的：「这次只回顾清单「035 办事师爷」（listId 为 xxx）里的
任务，别的清单和不属于任何清单的这次一概不看……」。他一份清单放一个项目，所以那
是在问「**这一个项目现在怎么样了**」，不是在问全局。

带了范围就**照它筛**：`data/tasks/` 里 `listId` 不等于那个 id 的，这一轮当作不
存在——不提建议，也不进 `insights` 的 `taskIds`。

- **`insights` 也跟着收窄。** 这一节最容易漏的就是它：跨任务观察天然想跨着看，但
  这一轮你手上只有这一份清单，「你最近老是把任务拖着」这种话是拿一份残缺的数据下
  的全局判断。范围内的观察照写（「这个项目有三条都卡在等同一件事」），范围外的
  留到下次全量回顾。
- **筛的判据只认 `listId`，不认清单名。** 名字会改，也可能撞——那句话里写出名字
  只是为了让这段话读得懂。
- 调接口那条路上（设置里选了「调接口」），你收到的 `data/tasks/` **已经筛过了**，
  提示词里会写明「全部 N 条里的 M 条」。这时候别因为「才几条任务」就觉得他很闲，
  那是范围，不是全貌。
- 没带这句话就是全量，跟以前一样。

## Step 3: 组装 updates/insights，写 outbox

```json
[
  {
    "updates": [
      {
        "id": "已有任务的 id",
        "patch": { "due": "…", "reminders": [{ "at": "…", "firedAt": null }] },
        "reason": "过期五天了，看起来卡在等外部回复——往后挪一周"
      }
    ]
  },
  {
    "insights": [
      { "kind": "pattern", "text": "…", "taskIds": ["…"] }
    ]
  }
]
```

两种条目要分数组里的不同项，不能塞进同一个对象——形状细节见 `AGENTS.md`。

原子写：先写 `outbox-<unique>.json.tmp`，写完整再改名成 `outbox-<unique>.json`。
临时名不能是 `outbox-` 开头又 `.json` 结尾，理由见 `AGENTS.md`。

**一条都没挑出来是正常结果**，如实说「这一轮没什么要改的」就行——不要为了凑数
造一条建议出来，那比不提更糟：他每看一条没用的建议，下一条真有用的就少一分信任。

## Step 4: 回复里说清楚

提了几条、分别为什么。他要能在不打开网页的情况下判断你这一轮跑得对不对。

## 这个不是自动跑的

`/expand`（拆收件箱）默认会在收件箱安静下来之后自动触发；**回顾不会**。
它是第二个会自己花订阅额度的东西，每次约 90 秒，节奏他还没说过，
所以只在他明确要的时候跑：终端里 `/review`，或者他自己排的定时任务。
