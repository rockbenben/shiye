## 一、P0 · 死胡同与不可自愈

### 1. AI 判「这不是任务」之后，用户被卡住且不知道自己被卡住

- **现象**：AI 拆完判某条收件箱记录「不是任务」→ `server/src/outbox.ts` 的 `mergeOutbox`
  把 `processed: true` + `taskIds: []` 一起落盘 → 那条从「待拆解」消失、掉进折叠的
  「已拆 N 条」，行上只写 `已拆 0 条`（`InboxSidebar.tsx` 里那段 `.ink-note-meta`）。
  而「变成任务」那颗**只在未处理分支里**，已处理分支只剩「重新拆解」「删除」
  （`InboxRow` 的 `actions` 三元）。也就是说 AI 恰好判断错时，用户唯一顺手的路恰好没了；
  想回到有出口的状态得先猜出「重新拆解」→ 填一句话说明 → 再等 92 秒。
- **滴答怎么做**：滴答收件箱里躺的**本来就是任务**，不存在这个中间态。收集箱的条目可以直接
  编辑成任务。（`docs/dida365/添加任务.md`，https://help.dida365.com/articles/6950658877373284352 ）
- **建议改法**：`InboxSidebar.tsx` 的 `actions` 里，`x.processed` 那一支加上「变成任务」，
  **但只在 `(x.taskIds ?? []).length === 0` 时给**——拆出东西了再变一条就是重复，
  `InboxSidebar.test.tsx` 里那条「已经拆过的没有这颗」正是在钉这个条件（夹具是
  `taskIds: ['t1']`）。同时把 `已拆 0 条` 改成一句实话。
- **为什么是 P0**：触发条件（AI 判断失误）在这个产品里是常态而非例外。这是整条 AI 链路上
  唯一一个「用户被卡住且不知道被卡住」的状态。
- **状态**：**已改**（批次 A）。

### 2. 竖栏整条消失，设置和搜索跟着一起没——而恢复入口就在设置里

- **现象**：竖栏上摆的是 `views` + `more` 两段（`lib/views.tsx` 里那个 `RAIL_GROUPS`）。
  把这六项**全部**设成「隐藏」→ `railDefs` 为空 → `App.tsx` 渲染竖栏那道
  `{railDefs.length > 0 && …}` 让整条 `Rail` 不渲染。而**「搜索」和「设置」两颗按钮
  就长在 Rail 里面**（`Rail.tsx` 末尾、`<nav>` 外面的那一对）。
  于是全应用没有任何入口能打开设置，而唯一能改回「显示」的地方就是设置本身。
  命令面板里没有「设置」这条命令（`App.tsx` 那份 `commands` 没有），`lib/keymap.ts`
  也没有 settings 动作。**只能手改 localStorage 的 `navModes` 才能复活。**
- **滴答怎么做**：设置挂在**头像 → 设置**，是一条恒在的路径，不挂在任何一个可关的模块栏上。
  （`docs/dida365/用清单管理任务.md`，https://help.dida365.com/articles/6950654234933067776 ）
- **建议改法**：`App.tsx` 那道条件改成恒真。`Rail` 本身已经能在 `items=[]` 时立住——
  `Rail.test.tsx` 里那条「空 items 不崩」钉的正是这一条。空栏时 mark 底下直接是
  搜索/设置两颗，语义正好。
- **为什么是 P0**：四条里唯一一条**不可自愈**的。而且触发它的动作恰恰是
  `lib/navVisibility.ts` 顶部那段明确推荐的做法：「把用不上的模块收起来」。
- **状态**：**已改**（批次 A）。

### 3. 数字键 `1`–`9` 数的是注册表顺序，不是屏幕上可见的顺序

- **现象**：数字键查 `NAV_VIEW_SPECS[action.index]`（`App.tsx` 的键盘处理里），
  而 `NAV_VIEW_SPECS = VIEW_SPECS.filter(不跳过 search)`——**整份注册表，
  不过 `visibleViews` 过滤**。侧栏真正渲染的是 `navDefs`。用户在任何一项上选「隐藏」
  （`SettingsModal.tsx` 那个 navModes 设置），那一项从侧栏消失，但**数字键序号不收缩**：
  按 `3` 跳到一个不在导航上的去处。命令面板的 hint 用同一份表，于是面板上标着「3」
  的那条屏幕上找不到对应行。快捷键表那句「切到导航上第 1～9 个去处」
  （`ShortcutHelp.tsx` 的表里）直接变成假话。
- **滴答怎么做**：数字键绑在侧栏上**真实存在的条目**上——它是侧栏那一列的快捷方式，
  侧栏显示什么就直接决定键位。滴答的显示状态是「显示 / 隐藏 / 有内容时显示」三档，
  是**侧栏的显示状态**，键位跟它同源。（`docs/dida365/用清单管理任务.md` 同上 URL）
- **建议改法**：`NAV_VIEW_SPECS` 改由 `navDefs` 推导，数字键处理与命令面板 hint 一并改读
  这份；`views.test.tsx` 的 `first9` 与 `App.test.tsx` 里那条顺序断言改成对同一份推导跑。
  改完**补一条「隐藏某项后仍一致」的用例**——现在没有任何一条测试会发现这个洞。
- **风险**：`views.test.tsx` 的「表顺序按段连续」那条、`App.test.tsx` 里那条、
  `README.md` 里抄的那份名单三处会一起红。**要一起改，不是绕过。**
  注意 `App.test.tsx` 里已经有「快捷键的顺序跟导航上显示的顺序完全一致」——它就在现场，
  只是因为用的是默认 `navModes`（全显示）才绿着。
- **状态**：**已改**（批次 D）。数字键改读一个 `navOrderRef`（判据是 `navDefs` 再过
  一层 `SKIP_IN_NAV`）；命令面板保留全量条目、只给可见的前 9 项发 hint。
  **补了一条它本该有的用例**并证伪过：原来那条断言用的是默认 `navModes`
  （全显示），修复前后都是绿的，洞就是从它下面漏过去的。新用例把「未归类」
  设成隐藏（选正中间是为了让按 5–9 全都验得到），从 DOM 读 Sidebar 真正渲染的
  导航标签逐位对照。回退修复后它立刻红：`expected '未归类' to be '按来源'`。
  另外按 `App.test.tsx` 顶部那条规矩加了 `navModes` / `navDefaultsV1` 两个清理键。

  **过程中被测试抓到一个我自己写的 bug**：`navDefs` **本身不过 `SKIP_IN_NAV`**
  （Sidebar 是自己渲染前才跳掉「搜索结果」的），漏了这一层会让「搜索结果」被算成
  第 1 项，按 `1` 跳到一个只在打字之后才出现的去处。断言原话是
  `expected '搜索结果' to be '收件箱'`。

- **窄屏的实话**：390 宽下新记号会落在右缘那道 mask 后面——跟已有的 `startAt`
  多天 chip 是同一个既有取舍（那条的注释就写着「整句会把该看的截止时间挤进右缘
  那道 mask 里静默消失」），不是新缺陷。实测 1280 宽 8 行全部不溢出。

### 5. `section`（分段）填了之后，七成界面看不见

- **现象**：`TaskFields.tsx` 的 `DraftAttr` 有 `'section'`，`emptyDraft()` 带它、保存也带走，
  但渲染处零命中：`TaskCard.tsx` grep `t.section` 只命中填草稿和存草稿两处；
  `TaskRow.tsx` 零命中。它只在 `lib/grouping.ts` 的 `groupBy:'section'` 被当组头用。
  同一份数据在「按分段分组」那一个视图里看得见，其它七个视图里完全隐形。
- **滴答怎么做**：分组（section）是清单里的常驻结构，以分组标题呈现，任务行本身不重复报——
  **滴答也不在行上画分段名**，但它的分组头是显式结构，而我们的 `section` 是一串自由文本、
  可以手打、可以在任何视图生效。（`docs/dida365/用分组和排序管理任务.md`，
  https://help.dida365.com/articles/7054273336087412736 ）
- **建议改法**：**做一次决定就行**，现在两头不靠才是问题。①在卡片标签行旁加一枚
  `.ink-section-mark`（与 `.ink-context-mark` 同一档），`TaskRow` 同步；②若判定「分段只该在
  分组视图里说」，把 `section` 从 `DraftAttr` 挪到只在 `groupBy==='section'` 时可见的入口。
- **风险**：方案 ① 不动 `DraftAttr`，只加渲染，不撞 `TaskFields.test.tsx`（它拿真渲染的
  `aria-label` 比 `ATTR_NAME`）。
- **状态**：**已改**（2026-10-16）。卡片与行档都画出来了，正文前面加 `§`——
  **这个前缀是拍图逼出来的**：填上分段一拍，就看出它和情境紧挨着、同一种视觉，
  读出来是「师爷 调研 整理 健康」这样一串裸字，哪个是哪个分不出来。`§` 是「节」的
  国际通用符号，跟情境那颗 `@` 一眼分得开，只占一个字符。**单测从头到尾都是绿的**
  （`overflowing: 0`），只有拍图能发现。
  **没有照抄滴答**：滴答任务行上也不重复报分段，但它那个分组头是清单里显式建出来的
  结构，而我们的 `section` 是能凭空打上去的自由文本——填它的理由跟站在哪一屏无关。

## 三、P2 · 视觉硬缺陷（可客观判定，不靠口味）

### 8. `theme.css` 里一个游离子体系的魔数色，对比度实测不达标

- **现象**：`.ink-note-done .ink-note-text` 那条规则原来是字面量 `#7c828b`，
  是整份样式表里**唯一**一个不走 token 的前景色。两个问题：
  1. **色相**：R124 G130 B139 是冷蓝灰（蓝>绿>红），而 `:root` 顶部那段注释说这一整套
     中性色是暖的（色相 30–40°），头一版全落在 219–240° 那段蓝里、已被判定「跟手稿立意
     对不上」整体转掉。这处是那轮改漏的残留。
  2. **对比度**：实测对 `--sheet` 是 **3.65:1**、对 `--paper` 是 **3.31:1**。
     它是 14px 正文，按 4.5 的门槛**两处都不合格**。对照 `--dim` 在同样两种面上是
     6.30 / 5.71。
- **它为什么能漏过去**：`theme.css.test.ts` 那节对比度断言全走 `token()` 读具名变量，
  **字面量是它们的盲区**。这不是某条断言写得不够严，是这一族断言的**形状**决定了它
  看不见不走 token 的颜色。
- **建议改法**：换成 `var(--dim)`。真正的价值在补守卫——**把字面量本身变成不允许的东西**
  （连 `rgb()` / `rgba()` / `hsl()` 一起扫），只要没有字面量，上面那几条的盲区就不存在。
  真需要新颜色时，正确做法是给它一个具名 token，再在对比度断言里定下量出来的比值。
- **状态**：**已改**（批次 C）。守卫**证伪过**：临时把 `#7c828b` 注回去，守卫立刻红，
  恢复后探针已不在文件里。

### 9. `.ink-frow-smart` 压破了全站 11px 字号下限

- **现象**：那个标记的 `font-size` 原来是 10px，是整份样式表里唯一一个低于 11px 的字号。
  而 11px 下限在本仓库有明文立规——`:root` 那段注释里写着「11px 是全站字号下限」，
  另有六七处注释都把它当既定事实引用。
  另有两个半档孤例（`.ink-frow` 的 13.5px 和 `.ink-composer textarea` 的 14.5px），
  没有注释解释为什么是半档。
- **建议改法**：提到 11px。半档那两处推荐**并到整档**（13px / 14px）——13.5 / 14.5 在 antd
  的 `controlHeight` 体系里没有任何对应物，而 `.ink-frow` 的 `min-height: 32px`
  已经把高度钉死了，半档字号对密度没有贡献。
- **风险**：低。`theme.css.test.ts` 对这三处只查 `min-height` / `text-align`。
- **状态**：**已改**（批次 C，10px → 11px）。两个半档孤例**未改**，属清理性质。

### 10. 看板在窄屏从未被量过，而且是全表唯一靠横向滚动兜底的列表

- **现象**：`.ink-cells`（看板）是全表唯一一条在窄屏靠 `overflow-x: auto` 兜底的列表
  （配 `flex: 1 0 200px`），四列 × 200px + 3×22px 缝 = 866px。而 `.ink-cells-2x2`
  （四象限）早就拆了单列，**看板没有对应的窄屏规则**。
  `tools/design-preview/batch1.html` 那 100+ 格里**一格都没量过「看板 · 手机 390」**。
- **建议改法**：**先量不改**。在 `batch1.html` 现有那格旁加两格（390×844，以及横滚到最右
  那格），先拿到数。按 `batch1.html` 头注释自己的判据（「先量出来再决定改谁」），
  这格应排在任何看板布局改动之前。**不要**先写 `@media` 改布局。
- **风险**：低。`batch1.html` 在版本库里但不在安装包里。
- **状态**：**已改**（2026-10-16）。实测（390×844，`listMode=board` + 一份 5 列清单）

### 16. ~~改个标题可能让已响过的提醒再响一次~~ —— 查完了，**不是 bug**

2026-10-16 实读 `server/src/mutate.ts` 的 `applyTaskPatch`：

```ts
const reminders = patch.reminders
  ? patch.reminders.map((r) => ({
      at: r.at,
      firedAt: prev.reminders.find((p) => p.at === r.at)?.firedAt ?? null,
    }))
  : undefined;
```

**服务端完全丢弃客户端发来的 `firedAt`**，按时刻去旧数组里回查：响过的提醒保留它的章，
新时刻才算「还没提醒过」。那里的注释还写了为什么——「reminders 把时刻和章绑在同一个
字段里……客户端发上来的一定是整个数组」，所以不能靠 patch 里有没有 `firedAt` 判断意图。

所以网页编辑整份回传 18 个字段**不会**让提醒重响。这条从待验证里划掉。
（审计报告和一路转述都只标了「推断」，这次读代码才落定——**推断和实测的差别就在这里**。）

### 17. ~~`FRESH_NAV_MODES` 的启动时序~~ —— 查实并修好了（2026-10-16）

**推断成立，而且比推断更糟。** `App.tsx` 里 `ensureNavDefaults()` 排在
`useState(() => getNavModes())` **之前**（先落记号后读），而那段注释自己写的是
「落上，**然后才读**」——代码跟自己的注释说的不是一回事。

**光把两行对调也修不好**：`getNavModes()` 只解析 `navModes` 那一个键、**根本不碰
`FRESH_NAV_MODES`**；真正读它的是渲染时的 `effectiveDefault`，而 `visibleViews` 是在
**同一次渲染的后半段**才被调用的，记号在那之前就落上了。所以新默认必须**物化进返回的
那一份**——修法是 `lib/navVisibility.ts` 的 `initialNavModes()`，三步按序发生。

**为什么单测一直是绿的**：那组测试全都**直接调 `visibleViews(defs, {}, …)`**、自己传
一份空 `navModes` 进去，压根覆盖不到启动这条真实路径。

**连带 10 条 `App.test.tsx` 变红**（不是 11，排查标的那个「不确定」不存在）。逐条读过
之后：**没有一条在守「这些入口必须在导航上」**——7 条只是拿「已完成」当跳板（判据在下一
行：hash / heading / groupSelect 值 / 表单是否消失），1 条钉的是序号位置，2 条分别因为
「空状态要求 done 空着」和「判据长在导航项数上」不能简单改。分别处理见各自的注释。

**⚠️ 仍开着的一个产品问题**：收窄之后，**一个空的「已完成」从侧栏点不进去了**——
那屏只能靠 hash 或命令面板进（命令面板的条目来自全量 `NAV_VIEW_SPECS`，所以跳得过去）。
这是收窄默认的直接后果，不是 bug，但要不要这样，是产品取舍。

**状态**：**已改**（`lib/navVisibility.ts` 的 `initialNavModes()` + `App.tsx` 接线 +
10 条测试改前提）。全量 184 文件 / 5946 条全绿。

`lib/navVisibility.ts` 给 `trash`/`done`/`nolist` 定了 `'auto'` 默认，但 `App.tsx` 的
`ensureNavDefaults()` 写在组件体里、紧挨着 `useState(() => getNavModes())`——
渲染第一帧就把记号落上了，之后 `freshDefaultsUsed()` 恒为 true。单测绿是因为它直接调
`visibleViews` 绕开了启动顺序。**结论是推断不是实测**（要跑起来看 localStorage），
落地前先验。

## 八、桌面版专项（2026-10-16 16:49 补做）

### A. 真实窗口与缩放

- `desktop/src/main.ts` 的 `createWindow` 里 `new BrowserWindow({ width: 1200, height: 800 })`，
  **没有 `minWidth` / `minHeight`**，也没有 `frame` / `titleBarStyle` 覆盖（标准边框）。

  这台显示器是 **150% 缩放**。两个数都不是错的，是两套坐标系；

- 用户数据在 `%APPDATA%\shiye`（**不是**产品名 `办事师爷`），其中 `agent\data\` 才是
  服务端读的那份（`paths.ts` 的 `resolvePaths`：打包后 `agentCwd = <userData>/agent`）。
- 应用自带服务监听 `127.0.0.1:30035`（端口是挑的，不是 30096）。

### C. 尺寸扫描（含无最小窗口尺寸这条风险）

`BrowserWindow` 没设下限，所以扫了小窗口。**结论：降级是对的，不需要改。**

| 视口 | 外壳 | 设置弹层 |
|---|---|---|
| 1200×769（默认内容区） | 无横向溢出，无控件落到折线以下 | 920 宽，纵向装得下 |
| 1000×700 | 无横向溢出；长标题正常出省略号 | 920 宽 |
| 900×600 | 无横向溢出 | **876** 宽（`max-width: calc(100vw - 24px)` 生效） |
| 800×600 | 无横向溢出 | **776** 宽，同上；`保存` 不滚就够得着 |
| 760×560 | 页面开始纵向溢出 | **736** 宽；`保存` **落在折线以下**（滚得到） |

最后两档说明一下：760 已经掉进窄屏断点（<768），布局整个换成竖排 + 横向滚动导航，
`max-width: calc(100vw - 24px)` 这时才开始真正起作用（1200 那档它没触发，弹层是满的 920）。
**760×560 那一档的「保存」在折线以下**——根因是 antd 弹层默认 100px 顶偏移，
560 高的视口只剩 460px 给弹层。页面本身有滚动条，滚得到，所以是**降级不是断裂**；
不是这几轮引入的回归，先记着不动。

**设置弹层的纵向是真紧的**（`theme.css` 的 `.ink-set { max-height: 70vh }`）：
769 高的内容区里，AI 拆解那一节可视 481px / 实高 1040px，**开局有 559px 在折线以下**——
用户抱怨的「地址 / 模型 / 密钥」正好被折线劈开：地址看得见、模型半截、密钥不见。
`.ink-set-body` 能滚（有滚动条），但那一屏开局是残的。

### D. 任务行右缘：量错了三次，结论是**没有 bug**

真包实拍里那条长标题（`Translation Occasionally Fails: …`）的元信息看着像被切了。
浏览器里量：1100～1600 每一档都有子元素越过行右缘（3～96px），越界的是
`.ink-trow-subcount`——**批次 B 补的第四枚记号**，看着像自己引入的回归。

**三次都量错了**：`.ink-trow-meta` 本来就是 `flex: 0 1 auto; min-width: 0; overflow: hidden`，
而 `.ink-trow-title` 带 `min-width: 4.5em`（规则注释里明写「标题先让路，元数据可以被挤」，
被挤掉的记号静默消失是**有意**的）。**`overflow: hidden` 只裁视觉、不改子元素的
`getBoundingClientRect()`**，所以「子元素越出行右缘」这个判据在有裁剪祖先时是假的。
改成走裁剪链（找 meta 与行之间到底有没有装不下它的裁剪祖先）后：
**没有任何一行的 meta 越出行右缘**——是设计行为。

（同一个错误形状这一天出了三次：`.ink-setmodal .ant-modal` 从未匹配、
`.ant-modal-body` 不是滚动容器、被裁子元素的矩形当溢出。**判据必须落到「实际会不会画出去」，
不能落在某个矩形的几何关系上。**）

### E. 「调接口」在真桌面版里走了一遍（2026-10-16 18:00）

上一节只是外壳。**调接口这一屏是在新包自己的渲染进程里量的**（CDP 9444，
内容区 1186×763 / dpr 1.5，弹层正文可视 **478px**）。

真包确认生效的：`width: "920px"`、`maxWidth: "1162px"`（= 1186 − 24）；
**侧栏只剩 7 项**（专注 / 数据与服务 / 关于 默认收起，导航收窄那批生效了）。
本机真实配置：`aiMode: cli`、`aiCli: agy`、`aiCliPath: ''`、
**`aiEndpointId: ''`、`aiEndpoints: {}`**——一条接口记录都没有。

**⭐ 找到一个真问题：点「更多厂商（N）」把正要填的模型和密钥埋掉了。**

| | 芯片 | 「接口地址」那一项 | 模型起始 y | 折线以上？ |
|---|---|---|---|---|
| 收着 | 10 颗 / 2 行 | 220px | 580 | 是（< 478 那条线） |
| 展开 | 32 颗 / 6 行 | **374px** | **735** | **否，差 71px** |

差值**全部落在「接口地址」这一项上**，没有别的东西在长（逐项高度对拍过）。
而这件事的后果正好打在这个交互的目的上：点开是为了挑一家，挑完要填的模型和密钥
却滑出了可视区，于是「挑一家 → 往下滚填 → 往上滚再挑一家」来回几趟。

**改法**：那 N 颗限高 100px 自己滚（`max-height` + `overflow-y: auto`，内联在
`AiSettingsSection.tsx` 那个 `Space` 上——相邻的「快速选型」芯片排本来就是内联写的，
没有新增类名、也就没有新增前缀族要登记）。展开只多花约 50px，模型/密钥留在折线以上。
跟 `.ant-dropdown-menu` 那条（`max-height: calc(50vh - 32px)` + `overflow-y: auto`）
是同一个理由、同一个做法：那份的菜单一格在屏幕外面时**是真的点不到**，这份不是，
但代价一样是用户在原地打转。**代价记在代码注释里**：想翻最后几颗得在这一小框里滚，
两层滚动比一层啰嗦；**不改成下拉**是留着的余地（把剩下 22 颗收进一个选择器彻底不占地方），
那是一次更大的交互改动，不在打磨范围内。

守卫写在 `AiSettingsSection.test.tsx`：钉的是**限高 + 自己滚**这个形状、限高值落在
80–120 之间，而不是钉死 100px（改高度时顺手动一下即可）。**已证伪**：把限高拿掉，
测试立刻红在「展开后的厂商芯片没有限高」。
