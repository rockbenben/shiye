# 桌面版冒烟清单

## 补一条（task-3：拖拽换成 @dnd-kit）：鼠标真的拖，不只是键盘

**这条验的是 jsdom 测不到的那一半。** `npm test` 里看板/四象限/今天三处的
拖拽用的都是键盘序列（Tab 到抓手→Space 拿起→方向键移动→Space 放下）走
`@dnd-kit` 的 `KeyboardSensor`——这条路径是真实的、有测试盯着。但
`@dnd-kit` 的指针传感器（`PointerSensor`，真实用户拖鼠标/触屏走的那条）
需要浏览器的指针捕获语义（`setPointerCapture`、连续的 `pointermove`），
jsdom 不实现这些，写不出真的用鼠标拖拽的自动化测试——这是这一批换库
之后新出现的、只能靠人核对的一段，以前原生 HTML5 拖放（`draggable`/
`dragstart`/`dragover`/`drop`）在 jsdom 里至少能模拟得动。

~~另外一条……`over` 理论上可能是 `null`……jsdom 里也验证不出来~~——**这条
后来证伪了（复审修复轮 1 · I1）**：`vi.mock('@dnd-kit/core', …)` 部分替换
（只在真实 `DndContext` 外面包一层，把它收到的 `onDragEnd` 存下来，其余
全部走真实实现）就能直接拿到 `TaskGrid.tsx`/`TodayView.tsx` 里真实的
`handleDragEnd` 函数、手工喂一个 `over: null` 的事件——不需要真的在 jsdom
里演出一次「拖到放置目标之外」，两个文件的测试里都补了这条（守卫 I1
那两组），**在 jsdom 里就能跑，不用等到这里人工核对**。

- [ ] **看板**：鼠标按住一张卡的抓手（圆点图案，卡片右上角/行左侧悬停出现的
      那个）拖到另一列，松手，确认状态真的改了、列表刷新到位。同一格内拖动
      经过另一张卡时，那张卡不该有任何视觉位移（复审修复轮 1 · I5：格子内
      顺序从来不是排出来的，之前默认的 reflow 动效会让别的卡「让位」，视觉
      上演一次其实不会发生的重排，现在关掉了这个动效，只有被拖的那张卡自己
      跟手移动）。
- [ ] **四象限**：同上，横向拖（同一行内）不该改「重要程度」，纵向拖（换行）
      应该改；同格不该有让位动效，跟看板同一条理由。
- [ ] **今天**：鼠标拖抓手调整顺序，松手确认新顺序真的落盘（刷新页面顺序
      还在）。**这里的让位动效跟看板/四象限不一样，是保留的**——「今天」的
      顺序是真的由拖拽结果决定，`@dnd-kit` 自带的 reflow 动画取代了以前手画
      的那条插入线，拖的过程中其它行会跟着让位，应该看起来顺畅，不该有跳变
      或者卡顿。
- [ ] **该看到什么**：跟键盘那条路结果一致（同样的状态变化、同样的顺序），
      拖拽手感顺滑，没有明显卡顿；鼠标中途松开在空白处（比如窗口外、页面
      其它无关区域）应该等价于「取消」，不该误触发任何改动。

这份清单验的是「读起来对」以外的那部分——托盘、窗口行为、原生通知真的弹出来、
打包出的 exe 能不能跑，这些东西没有 GUI 的环境测不了，只能靠人在自己机器上走
一遍。按顺序做，每条都写了「怎么做」和「该看到什么」；出现「该看到什么」以外
的结果就是没通过。

先跑 `npm run dist:desktop`，产物在 `desktop/release/` 下：免安装版
`办事师爷-<版本号>-win.zip`，安装版 `办事师爷 Setup <版本号>.exe`。免安装版**先解压到
一个固定文件夹**（别在压缩软件的临时预览里直接双击），跑的是里面的
`办事师爷.exe`。**第 4/5 条（原生通知）必须用安装版走**——免安装版没有开始菜单
快捷方式，Windows 不给它弹通知；别的条免安装版都行。

第一次双击大概率会被 SmartScreen 拦一下（没签名，个人使用没买证书）——点
「更多信息」再点「仍要运行」，之后正常走。

**走第 4/5 条之前先确认**：系统「设置 → 系统 → 通知」里没有整体关掉通知，
「专注助手」不在开启状态——这两个开着的话通知会被系统吃掉，跟桌面版本身
有没有问题无关。

## 1. 双击 exe，窗口开出来，看板是空的（这是对的）

**怎么做**：双击解压好的 `办事师爷.exe`（或安装版装完的快捷方式）。

**该看到什么**：一两秒内弹出一个窗口，看板加载出来——**点下去超过十秒还什么都
没有就是不对的**，那是曾经用 portable 单文件产物时的症状（每次启动都要重解压
375 MB，全程没有任何反馈，看着就是「点了没反应」），换成 zip 之后不该再出现；
真遇上先确认跑的是解压出来的那个 exe，不是压缩包里的——**第一次启动看板是空的，
这是对的**：桌面版有自己的一份数据在 `%APPDATA%\shiye\agent\data\`，跟仓库里
的 `data/` 是两份，不共享。不该白屏、不该停在空白页超过 10 秒——超过 10 秒
会换成一句「服务没能在 10 秒内应答」的说明页，出现这个说明页就是没通过，去
任务管理器确认有没有 `办事师爷.exe` 在跑、看它有没有报错。

**验收改成**：在这个空看板上新建一张卡，刷新页面（或者关窗口再从托盘打开），
那张卡还在。

## 2. 关掉窗口 → 窗口消失，托盘还有图标，进程还在

**怎么做**：点窗口右上角的关闭按钮（×）。

**该看到什么**：窗口消失，但没有像普通程序那样退出——任务栏右下角的托盘区域
（可能要点那个 `^` 展开隐藏图标）还能看到应用图标。打开任务管理器，「详细信息」
标签里应该能看到**两个 `办事师爷.exe`**（一个是界面，一个是后台服务——服务子进程
用 `ELECTRON_RUN_AS_NODE=1` 把 `办事师爷.exe` 自己当 Node 跑，不会有单独的
`node.exe`）。**这一条是整批「Electron 接线」的验收核心**：关窗口不等于关服务。

## 3. 托盘左键 → 窗口回来

**怎么做**：左键点一下托盘图标。

**该看到什么**：窗口重新出现并且是激活状态（能直接在上面打字/点击，不用
再点一下才聚焦），看板上的内容跟关窗口之前一致，没有重新加载丢状态的感觉。

## 4. 设一个一分钟后的提醒 → 关掉窗口 → 一分钟后弹出原生通知

**这是这一整批的验收点。**

**怎么做**：在看板上随便找一张卡（或者新建一张），编辑它的「提醒时间」，设成
当前时间往后一分钟。存下之后**关掉窗口**（回到第 2 条的状态：托盘还在、
窗口不在）。什么都不用做，等一分钟。

**该看到什么**：大约一分钟后（服务每 30 秒扫一次到期任务，所以最多再多等
30 秒），屏幕右下角弹出一条 Windows 系统通知，标题是「该做了」，内容是那张
卡片的标题。这条通知不需要窗口开着才能弹——如果窗口是关着的（托盘状态）它照样
要弹出来，这正是桌面版要解决的问题。**通知上应该能看到应用图标**（跟托盘图标
是同一张），**通知下方应该有两个按钮：「完成」「推迟 10 分钟」**——这几条是
Task 2 新加的，之前的版本弹出来的是没有图标、没有按钮的系统默认样式，见下面
「补两条」。

## 5. 点那条通知 → 窗口回来，并且定位到那条具体的任务

**怎么做**：点第 4 条弹出的那条系统通知本身（不是点它下面的按钮，是点通知
中间的内容区域）。

**该看到什么**：窗口打开并聚焦，**而且那张卡直接进入了编辑态**（标题输入框
自动聚焦，能看到这张卡的完整字段）——不是打开窗口之后还要自己去找是哪一张。
这是 Task 2 新加的行为（点通知带上了任务 id，网页那边切到装得下它的视图再打开
编辑表单，见 web/src/App.tsx 里接 `desktop-open-task` 事件那段），旧版本只会
把窗口带到前台，卡片停在原来的样子——如果看到的是旧行为，说明这条没接上。

## 6. 托盘右键「退出」→ 进程真的没了

**怎么做**：右键点托盘图标，菜单里点「退出」。

**该看到什么**：窗口和托盘图标都消失。**打开任务管理器确认**：**两个
`办事师爷.exe`**（界面 + 后台服务）都应该已经不在进程列表里了——不该留一个孤儿
进程继续占着端口 30035（可以顺手用浏览器打开 http://localhost:30035 确认
打不开了）。

## 7. 先双击 `启动.cmd`、再双击 exe → 不该出现两个服务打架

**怎么做**：在仓库文件夹里先双击 `启动.cmd`，等它把浏览器打开、终端里打印出
「这个窗口开着，网页才能用」那行字之后，**再**双击桌面版的 exe。

**该看到什么**：桌面版的窗口正常开出来，看板内容跟 `启动.cmd` 那边一致——
**因为复用了同一个服务进程，看到的就是 `启动.cmd` 那份数据，跟第 1 条那份
空的不是同一份，这是对的**。**不该看到端口冲突的错误、不该弹出第二个进程**
——桌面版起服务前会先探一下 30035 端口上是不是已经有个健康的自己，有就直接
复用。之后退出桌面版（第 6 条那样），`启动.cmd` 那个终端窗口应该还好好开着、
没被带走——桌面版复用的场景下退出只应该关自己的窗口/托盘，不该把
`启动.cmd` 起的那个服务也杀掉。

**这个场景下不该再弹两次**：桌面版订阅 `/api/events` 时带的 `?client=desktop`
让服务端知道「桌面端在线」（`server/src/events.ts` 的 `Bus#isDesktopOnline`），
`fireReminders` 因此会把 `server/` 的 `toast.ps1` 那一路关掉，只剩 Electron
自己弹的那一条——不管服务是先被 `启动.cmd` 起来还是被 exe 自己起来，只要这个
桌面版窗口连着，就该只看到一条通知。如果两条都弹了，是这一批改坏了，不是
「正常现象」。

## 8. 拆解一条收件箱记录 → AI 真的跑起来

**这一条验的是 Task 1 的 `aiSeesSameData` 不变量**：桌面版把 AI 的工作目录
隔到了 `<userData>/agent/`，如果这个目录跟服务实际读写的 `data/` 对不上，
AI 拆解会被服务端直接拒绝（红横幅），不会是「悄悄没反应」。

**怎么做**：在桌面版窗口里，收件箱随便记一句话（比如「明天下午三点交房租」），
存下，点「立即拆解」（或者等自动拆解的倒计时跑完）。

**该看到什么**：一两分钟后，收件箱那条记录变成「已拆解」，看板上多出一张
新任务，标题、截止时间跟你写的原文对得上。**不该看到红色横幅说「服务在读 X，
而 AI 会去读 Y」**——出现这条就是路径没对齐，回去检查
`%APPDATA%\shiye\agent\` 下有没有正确铺出 `data/`、`AGENTS.md`、`workflows/`。
（**没有自动迁移**：装过更早那版打包应用的话，数据在 `%APPDATA%\待办\agent\`
——那一版的 productName 是「待办」，不是「办事师爷」，后者那个目录从来没有任何
安装包创建过。要保留旧数据就自己把整个 `agent\` 拷到 `%APPDATA%\shiye\` 底下，
然后重新跑这一步。理由见 `main.ts` 里 `setPath` 下面那段长注释。）

## 补一条（2026-08-19 加）：手动关掉系统通知，提醒有没有兜底

**这条验的是一个已知缺口，这个沙盒环境测不了，只能靠人在真机上确认。**

服务端现在靠「桌面版连着 SSE」判断桌面端在不在线，在线就不再起 `toast.ps1`
那条 PowerShell 兜底，只指望 Electron 自己的 `Notification` 弹出来。Electron
那边如果弹失败（`'failed'` 事件），桌面版会上报给服务端、服务端就地补发一次
PowerShell（`POST /api/desktop/notify-failed`）——**但这条上报只在 Electron
自己知道弹失败了的时候才会触发**。用户在「设置 → 系统 → 通知」里把「办事师爷」
整个关掉这种情况，Electron 不一定会触发 `'failed'`（这个沙盒起不了真的
Electron GUI，没法实测这条边界），那种情况下服务端收不到任何信号，会一直
以为「桌面端在线、不用兜底」，实际上一条通知都不会弹出来。

- [ ] **怎么做**：「设置 → 系统 → 通知」里单独把「办事师爷」这个应用的通知关掉
      （不是整体关，就关这一个应用）。回到桌面版窗口，设一个一分钟后的提醒
      （跟第 4 条一样的做法），关掉窗口，等一分钟多一点。
- [ ] **该看到什么**：这里目前**没有已知的兜底路径**——如果真的一条通知都
      没弹出来（既没有 Windows 通知，也没有别的提示），这就是上面说的那个
      已知缺口，不是意外；如果意外地弹出了 PowerShell 那条兜底通知（说明
      `'failed'` 事件其实触发了），把这个发现告诉我，说明这条边界比预想的
      更容易兜住，值得补一条测试钉住它。

## 补两条（2026-08-19 加）：通知上「完成」「推迟 10 分钟」两个按钮真的做事

**这条是 Task 2 里唯一一处这个沙盒完全验不了的逻辑，只能靠人在真机上点一次。**

按钮点击不走 Electron 的 `Notification.on('action')`（那条路在 Windows 上对
自定义 `toastXml` 不生效，`actions` 字段本身也是 macOS 专属）——两个按钮的
`arguments` 是协议 URI（`todo-desktop://complete?id=…`、
`todo-desktop://snooze?id=…`），点击后 Windows 把它当协议链接启动，命中
`main.ts` 里 `app.setAsDefaultProtocolClient('todo-desktop')` 注册的处理器；
因为办事师爷已经在跑、占着单实例锁，这次「启动」会在原来那个进程的
`app.on('second-instance', …)` 里收到，解析出按钮和任务 id 之后直接 PATCH
服务端，**不开窗口**（quick action 的意义就是不用打开应用）。

应用没在跑（托盘退出过、或者机器重启过）时留在通知中心里的旧 toast 被点，
走的是另一条路：协议激活拉起一个全新的进程，这个进程拿到单实例锁、正常走
`bootstrap()`——这种情况下窗口会正常打开（这是冷启动流程本身决定的，不是
故意为按钮设计的行为），但 `main.ts` 会在服务起来之后额外用
`routeSecondInstance()` 扫一遍 `process.argv`，判成协议 URI 就调
`applyProtocolAction`，任务照样会被改——这条路径跟应用已经在跑时（走
`second-instance`）判断走哪条路用的是同一个 `routeSecondInstance()`
（`desktop/src/protocol.ts`），下面两条验收各测一遍这两种情况。

这条链路里，URI 怎么解析出 kind/id（`parseProtocolUri`）、「完成/推迟」
各自要发什么 patch（`patchForAction`）、argv 该判成协议激活还是普通启动
（`routeSecondInstance`）——这三件事都不需要 Electron，抽进了
`desktop/src/protocol.ts`，有真实执行的单元测试（`protocol.test.ts`）；
`buildToastXml()` 拼出来的 `<action arguments="…" activationType="protocol">`
XML 也有单元测试守着。

**修复轮 3 加了一层**：`main.ts` 剩下的接线（点击 second-instance 处理器
真的 PATCH 了对的任务且没弹窗口、冷启动扫了 `process.argv`、点通知本体
派发的脚本安全转义了 id、协议真的注册了、toastXml 里没有 `actions` 字段）
现在也用 `vi.mock('electron', …)` 真的跑起来测了（`main.test.ts`），不再是
只查字符串在不在文件里——之前「拿一行注释顶掉真代码、字符串还在文件里」
这种能溜过源文本断言的坏法（复审用这招测穿过 5 条），现在会被这些真行为
测试当场抓到，包括「quick action 分支旁边多插一次 `openWindow()`」这种
换个名字也藏不住的回归。

**真正留下来、这个沙盒到底也测不到的，只剩一件事**：「Windows 点了 toast
按钮之后，真的会经过协议激活、真的会命中 `second-instance`/冷启动 argv
扫描」——这是操作系统和真实 Electron 运行时之间的联动，`vi.mock` 只能在
Node 进程里模拟 electron 这个模块的 API 形状，模拟不了 Windows 通知中心
会不会真的按 `activationType="protocol"` 拉起一个新进程、`app.on
('second-instance', …)` 在两个真实操作系统进程之间会不会真的收到转发的
`argv`。这件事从没有在真实 Windows 上跑过一次，属于报告里明确交代过的
「做不到就说清楚」那一类，下面这几条验收就是补这个缺口的。

**如果点了按钮完全没反应：这里老实说，没有可见的诊断信号。**
`main.ts` 里协议注册失败会 `console.error` 一行，但**这行日志没有地方能看到**
——`main.ts` 是打包后 GUI 子系统的 `办事师爷.exe`，没有终端窗口，主进程的
`console.error` 默认不落到任何地方；`启动.cmd` 起的是**服务**
（`node server/dist/index.js`），跟 Electron 主进程是两个互不相干的进程，
它的终端窗口里也不会出现这行日志。`npm run desktop` 能看到主进程输出，但
这个仓库明确禁止跑开发模式。**目前唯一能观察到的信号就是「按钮点了有没有
效果」本身**——按钮点了没反应的话，把这个结果直接告诉我，我会追加日志到
一个能实际看到的地方（比如写文件、或者在打包时给 `.exe` 加
`--enable-logging` 之类的诊断开关），不用先自己去找一个现在还看不到的日志。
